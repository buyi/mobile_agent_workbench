# Loopit 工作台分阶段规格

版本：v0.3；状态：评审稿；日期：2026-10-08。

四个阶段按可验证的交付能力递进。每个阶段都产出可运行增量、机器可读结果和交接清单，不能以页面完成、接口存在或模型自报完成代替验收。

| 阶段 | 规格 | 要证明的能力 | 交给下一阶段的结果 |
| --- | --- | --- | --- |
| M0 | [契约与接入验证](m0-contracts-and-integration.md) | 固定合同能约束真实 Runtime、设备、构建和发布操作 | 可运行控制骨架、已实测能力矩阵、首个目标及验证基线 |
| M1 | [真实功能自主交付](m1-autonomous-feature.md) | 现有 Loopit 小功能无人执行，从目标走到内部分发与观察 | 完整交付链、故障恢复证据、可重复的业务基准 |
| M2 | [日常工作台 v1](m2-daily-workbench.md) | 同一底座三端操控、日常场景、后台与最小经验学习 | 稳定版本、指标基线、版本化知识与评测基础 |
| M3 | [工作台自主迭代](m3-self-improvement.md) | 在长期目标约束下自主开发并升级自身，失败可回滚 | 有界改进循环、版本晋升体系和机器学习接入合同 |

## 1 共同依据与决策状态

所有阶段继承[产品与架构](../loopit-workbench-spec.md)、[执行契约](../execution-contracts.md)、[验收与评测](../acceptance-spec.md)、[参考与选型](../reference-and-selection.md)。共同不变量由执行契约定义，各阶段只细化范围、实现工作和阶段门槛；若需要改变不变量，应先修订关联规格并记录理由，不能在某阶段局部绕过。

已确认：首个业务闭环必须是现有 Loopit 移动端的真实小功能。尚未确认：具体功能、目标平台/设备、渠道和预算；产品主线「Project → Task → Run → Delivery」仍是提案。编写规格不依赖这些答案，执行相应工作前必须将所需参数冻结到输入合同。

用户已确认 OpenCode 作为唯一开源主工程及 Agent 运行时，沿用底座能力做 Loopit 扩展，见[ADR-0001](../decisions/0001-opencode-base.md)。M0 冻结具体发行版与合同映射并实测。首期 Android 真机、内部渠道仍是提案，不自动视为用户已选定。首验设备只证明该平台能力；另一平台和三种客户端分别验收。阶段参数缺失时可以推进独立基础工作，不能宣布整个里程碑 passed。

## 2 统一阶段交接合同

每阶段发布不可变 `MilestoneManifest`，至少包含：

| 字段 | 含义 |
| --- | --- |
| milestone / specDigest | M0–M3 与本次执行依据的规格摘要 |
| sourceRevision / contractVersions | 实现版本与冻结的合同版本 |
| upstreamManifestRefs | 上游已通过清单及摘要；M0 可为空 |
| inputRefs / outputRefs | 目标、策略、资源、产物和完整证据引用 |
| capabilityMatrixRef | Runtime、Worker、设备、渠道、客户端能力及实测范围 |
| testResultsRef / metricsRef | 本阶段每个必需用例结果、样本、成本、人工介入和性能 |
| unresolvedConstraints | 未满足条件、原因、影响范围、重试触发条件 |
| verdict | `passed / failed / blocked`；由阶段检查器签发 |

manifest 和证据由独立验证身份提交，构建者不能把自身记录直接改为 passed。所有必需测试符合预期且对应产物存在，阶段才 passed；依赖缺失为 blocked，断言不符为 failed。负向测试预期拒绝时，发生正确拒绝表示该测试通过，不等于被拒绝的业务任务成功。

`notRun`、未提供证据、未解析引用和未知外部副作用都不能计为通过。替换组件时保持验收语义并重跑受影响合同；不能通过移除失败能力或修改分母获得同一冻结范围的通过。

故障注入可以预期得到 blocked、indeterminate 或资源隔离；这只代表负向断言正确。整个测试套件 passed 前，必须撤除注入、通过独立核对恢复真实状态、清理资源并留存回执；遗留未知发布、活动旧进程或受污染设备时，阶段保持 blocked，不能把测试中的正确隔离当作永久清理完成。

上游版本变化后，下游按依赖摘要重新核对：合同、权限、验证器或平台能力变化会使相关通过记录失效；无关文案修订不要求无条件重跑。继承的验收结果必须引用原证据与适用性判断，不能只复制一个绿色状态。

## 3 实施与并行边界

实施顺序为 `M0 → M1 → M2 → M3`。下一阶段的规格、设计和无副作用实现可以提前进行；依赖上游真实能力的集成与阶段验收必须等待有效交接结果。

M0 锁定 OpenCode 版本并固定合同映射后，交付扩展、原生 Runtime 合同验证、设备/构建连接器可并行。M1 以同一目标汇合；M2 的客户端、后台、日常工具和知识能力可并行；M3 的评测管理与升级控制可并行，最终以一次自身功能升级汇合。每个并行写入者使用独立工作副本，同一设备或发布资源保持独占控制。

合同、交付状态、执行、工具、验证、存储与客户端是职责划分，优先映射到唯一底座已有模块与扩展点，不要求新建 `control` 或 `runtime-adapters` 通用平台。实际目录沿用底座惯例并由 M0 ADR 记录。

## 4 验收责任划分

| 验收族 | 首次落实 | 后续重验 |
| --- | --- | --- |
| schema、幂等、版本、取消、沙盒、证据、租约 | M0 的合同与真实接入实验 | M1 业务全链路；M2 新客户端及同底座日常能力；M3 升级后 |
| E01–E06 真实功能交付、修复和恢复 | M1 | M2 代表业务回归；M3 旧版本与候选兼容 |
| S01–S23 稳定性边界 | M0 建立相关机制和测试，M1 贯通执行范围 | M2 全客户端及同底座能力矩阵；M3 升级与历史数据 |
| P01–P10 性能与耐久 | M0 建立计量和恢复实验；M1 验证实际交付拓扑、规定历史规模和 Web/API 负载 | M2 增加同底座三端、日常场景与连续运行；M3 晋升回归门 |
| 三入口与日常场景集 | M2 | M3 候选版本回归 |
| L01–L05 经验学习 | M2 最小记忆/skill晋升、撤回和隔离 | M3 实验与策略扩展 |
| 自主修改并升级工作台 | M3 | 后续每次自身发布 |

各子规格必须列出本阶段实际执行的条目及范围，不能用此表将安全和状态正确性延期。目标未涉及的产品平台可以不进入该次交付矩阵，但已经声明支持的能力不能因测试困难而删除。

## 5 执行与评审方式

每阶段采用相同交付顺序：读取输入 → 形成设计 → 实现切片 → 自动验证 → 构建/部署适用产物 → 运维与交接。短路遵循共同阶段合同；“工作台本身的开发”同样需要可追溯的产物链。

M0 的连接器和环境建设属于工作台的建设工作，不计作 M1 无人业务交付；M1 正式计时开始后的人为解锁、输验证码、修代码、补命令或改状态必须计为介入。自动化故障注入属于预先冻结的评测输入，不算人工救回，故障后的恢复必须由系统自行完成。

本文所有命令、文件形状和性能数值属于实施合同或工程目标，未执行项保持未验证。规格编写与后续执行是两个独立事实；本轮交付这四份规格，不宣称已经运行或通过 M0–M3。
