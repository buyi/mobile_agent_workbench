# M0 契约与接入验证规格

版本：v0.3；状态：评审稿；日期：2026-10-08。上游依据：[主规格](../loopit-workbench-spec.md)、[执行契约](../execution-contracts.md)、[验收规格](../acceptance-spec.md)。共同交接规则见[阶段总览](README.md)，底座约束见[单一开源底座决策](../reference-and-selection.md#0-当前决策单一开源底座)。

M0 要交付一个可以真实启动、观察、停止、恢复和核对执行的最小控制骨架，并证明首个 Loopit 目标需要的设备、构建、验证及分发能力可用。它不负责完成该业务功能；M1 使用 M0 的结果完成无人交付。

## 1 目标与范围

### 1.1 本阶段完成什么

- 落实已确认的 OpenCode 主工程及其 Agent 运行时，锁定具体版本，记录源码、许可、必要依赖和能力缺口，不以闭源 Agent 核心为必需前提。
- 将文字协议映射到所选底座的对象与扩展点，补齐可版本化、可校验的 schema 和状态规则。
- 运行并扩展底座的任务服务与执行进程，持久保存目标、执行、操作和证据；已有会话、工具和 Agent 循环直接沿用。
- 在目标 Loopit 工具链上验证一个明确设备路线、可复现构建和内部分发能力。
- 建立独立验证器、好坏样本、故障注入入口和成本/耗时/人工介入计量。
- 冻结 M1 的具体目标、策略、验收与资源清单，给出可检查的交接结果。

### 1.2 本阶段不包含什么

不实现完整三端产品、自有分析后台、自动模型路由、跨任务知识晋升或工作台自身升级。M0–M3 均不要求第二 Runtime。可以用底座 CLI/API 驱动合同实验，不要求漂亮 UI。纯代码样例只证明执行器合同，不能代替 Loopit 设备和渠道探测，也不能称为 M1 完成。

## 2 输入与进入条件

| 输入 | 开始依赖它的工作 | 条件不满足时 |
| --- | --- | --- |
| 本组规格与四层/五个 harness 边界 | schema、领域状态、目录设计 | 修正矛盾后再冻结合同 |
| 一个目标工作区与允许写入范围 | Runtime 编辑实验 | 可先做协议模拟；不宣称写入能力通过 |
| 运行凭据引用与授权策略 | 真实模型、工具调用 | 只运行无模型合同检查；目标能力保持未验证 |
| Loopit 仓库、基线和构建配置 | 构建/安装探测 | 输出结构化约束，不以历史包冒充当前构建 |
| 明确设备标识、类型、系统和测试 fixture | 设备验证 | 可以完成其他连接器，设备路线不标为 supported |
| 内部渠道、签名/分发凭据及可查询接口 | 发布幂等和核对实验 | 禁止声称自主部署可用 |
| 用户选定的小功能及验收、预算、交付范围 | M1 输入冻结 | 不阻塞独立基础工作，但 M0 总体不能 passed |

核心产品模型采用现有提案形成合同，界面术语后续可调整；原生 RuntimeSession 不得替代业务 Task。M0 不从诊断页示例、历史 iPhone 模拟器记录或 Android 建议推断用户已确认的功能/平台。

## 3 四层实施增量

| 层 | 本阶段实现 | 对外边界 |
| --- | --- | --- |
| 接入 | CLI/API 提交命令、查询任务与订阅事件；最小操作者身份 | CommandReceipt、查询投影、带游标的事件 |
| 编排 | 目标版本、Task/Run 状态、确定性 reducer、合同检查、预算、持久调度接入实验 | ExecutionSpec、StageResult、GateDecision |
| 执行 | Worker Supervisor、首个 Runtime Adapter、独立检查/构建执行器 | RuntimeCapabilities、事件、停止/恢复与清理回执 |
| 基础 | 底座原生持久化及必要扩展、产物库、恢复日志、策略/密钥、OS 沙盒、设备 Broker | Artifact/Evidence、Operation Ledger、租约与身份 |

harness 五个关注面都需出现最小实现：工具注册与能力探测；ContextManifest 与按需材料引用；候选经验条目及来源存储；目标/验证状态推进；沙盒与资源隔离。M0 的记忆只记录和检索来源，不自动晋升为生效规则。

技术基线随唯一底座确定，优先沿用其语言、服务、存储、调度和客户端协议。撤回 TypeScript 新控制服务、PostgreSQL 与 Temporal 的预设组合。合同是行为要求，Adapter、Broker、Supervisor 是职责名称，优先由底座机制和必要工具扩展承载；不另建通用多 Runtime 框架。候选不通过时记录缺口与最小改造成本，必要时替换整个底座，不能降低恢复或验收语义。

## 4 功能要求

### M0-F01 合同包

MUST 提供 GoalSpec、PolicyRef、ContextManifest、ExecutionSpec、StageResult、ArtifactEnvelope、Evidence、GateDecision、EventEnvelope、OperationRecord、RuntimeCapabilities 和 MilestoneManifest 的 schema 与解析接口。schemaVersion 是持久数据版本，不能与应用版本号混用。

验收 ID、requiredAtStage、证据依赖、对象引用、摘要和 enum 都可校验。非法输入在副作用发生前拒绝；不支持的 schemaVersion 明确返回不兼容。阶段 Gate 和最终交付 Gate 分开，设计/开发阶段不得要求未来发布回执。

### M0-F02 权威任务状态

MUST 支持 createTask、reviseGoal、startRun、pauseRun、cancelRun、resumeRun、getTask/getRun、subscribeEvents 的最小语义。重复 commandId 返回同一逻辑回执，expectedVersion 冲突不会覆盖现有目标。

命令回执、领域事件、投影、outbox 在同一事务落库；事件提交后再通知与派发。accepted 不表示外部执行完成。历史终态不可因目标修订改成 superseded；终态 Run 的重试建立新 Run，成本与目标预算继续累加。

### M0-F03 Runtime 生命周期

MUST 按共同 Adapter 合同实现 probe/start/observe/sendInput/cancel/inspect/reconcile/collect/dispose；checkpoint 等可选原生能力必须明确 supported、unsupported 或受限。

使用锁定的 Runtime 发行版本完成一次实际编辑与检查。prompt ACK、settled、进程退出和 Gate 通过分别记录。Runner 不继承无关的全局个人配置；有效指令、工具、模型、skills、路径和权限进入 ContextManifest。缺少特定原生能力可用合同允许的等价机制实现，不能假装支持。

### M0-F04 停止与暂停

取消和暂停接受后不派发新副作用，跟踪进程树、设备控制和外部作业。只有实际停止/清理已核对才给出最终停止状态；无法中断的外部操作继续核对并隔离资源。

原生不支持暂停时安全停止旧 Attempt、保存可重建事实，恢复创建新 Attempt；不保证保留私有内存。暂停跨控制服务重启仍然有效，deadline 与预算按共同合同处理，不重置目标预算。

### M0-F05 持久调度与恢复

MUST 在底座持久调度机制上用独立实验验证重启恢复、已提交执行结果复用与重复派发去重。模型调用、工具和外部 I/O 在执行边界中；恢复不重新推理已提交决定。不以要求“Activity”接口的方式隐含指定外部调度器。

上层与 Runtime 的重试次数分别可见并计入总预算。旧进程状态未知时，不创建会同时写相同工作区或控制相同设备的新 Attempt。

### M0-F06 副作用账本

每次发布、设备控制等外部动作必须有稳定 operationId、请求摘要、owner generation、幂等键、回执与核对方法。先入账，再派发，再补回执。回执丢失进入 indeterminate，查询事实后才能决定重试。

需核对或不可逆动作在 dispatch 前同步写入独立故障域的恢复日志。恢复旧业务快照时进入 recovery-only，以不随快照回退的授权边界签发新 recoveryEpoch；旧 token 不再生效。不能提供该保证的连接器不得执行此类自动副作用。单机进程实验不等同整机灾难恢复。

### M0-F07 沙盒与凭据

MUST 隔离工作副本、进程、可写目录、网络与秘密引用；worktree 不计作完整沙盒。Shell 与 Runtime 内置工具也受同一边界约束。Builder 无验证签发身份、发布凭据和根策略写权限。

密钥在可信代理执行时解析，不进入模型文本、日志、产物或候选记忆。目录、网络、直接设备访问和跨环境发布旁路都要做负向实验，不能只检查工具名白名单。

### M0-F08 设备 Broker

MUST 在一个明确的 Loopit 设备路线验证 open、inspect、snapshot、act、wait、lifecycle、evidence、close 及目标所需安装/网络能力。UI 操作携带 revision 与语义目标；歧义或 App 漂移必须重新观察。

所有写设备操作经过同一 Broker，租约包含实际设备身份、generation 与 epoch。外部 Panels/ADB 能绕过独占时，必须封闭该路线或判为不具备无人执行所需隔离能力。结束和故障后恢复网络/代理等被修改状态。

### M0-F09 构建与安装身份

MUST 从锁定 Loopit 基线生成一份真实测试构建，保存源码/补丁、依赖、配置、二进制及适用 JS bundle 摘要；在指定设备上安装并独立核对实际身份。不得只核对包名或展示版本。

无需实现新业务功能；已知基线用于证明工具链。每个目标平台独立产出结果，模拟器与物理设备分列。

### M0-F10 渠道能力

MUST 使用授权的内部测试范围验证已有基线构建的 publish、inspect、reconcile 和至少一种适用的停止分发/回滚机制。测试「外部成功但回执未落账」和「无法查询结果」两种情况；前者补记既有事实，后者不盲目重发。

本要求定义未来的 M0 实验范围，不授权本轮规格编写执行真实发布。外部副作用实验必须使用冻结 PolicyRef 中允许的渠道和资源。

### M0-F11 验证与证据入口

MUST 实现独立 Gate 最小检查器，验证必需证据存在、摘要/身份匹配、验收版本正确、来源有权签发。产物成功持久化后才能签发正式证据引用；底层最佳努力日志不直接作为持久完成回执。

每个验证器至少有已知通过、已知失败、缺失和错版本样本。模型的 UI 语义评估必须附固定 rubric 与观察引用；不能把模型回复当程序、设备或服务回执。Builder 修改验证器和签发结果的尝试必须失败。

### M0-F12 上下文、经验与计量

MUST 用 ContextManifest 重建目标、候选、策略、计划和最近有效证据；原生会话缺失时仍能解释当前状态。原始大日志与图片以引用按需读取，摘要不能覆盖原始事实。

保存带作用域、来源、版本与有效期的候选经验；本阶段不自动改变后续任务策略。记录模型/工具费用来源、unknown 费用、排队/推理/工具/验证耗时、每次重试和人工介入，确保后续后台有真实数据。

### M0-F13 选择结果与首个目标冻结

MUST 输出 ADR、Bill of Materials 和能力矩阵，锁定唯一开源底座与其 Agent 运行时，列明沿用/扩展/缺失、固定版本、可构建证据、核心与依赖许可、升级方式和实测结果。必需路径不得依赖 Claude Agent SDK/Claude Code 等专有 Agent 核心。模型 API 与系统工具授权独立登记。能力至少区分 supported、limited、unsupported、unverified。

M1 GoalSpec 必须将功能、验收、基线、平台设备、fixture、环境、渠道、观察窗口、预算和可回滚范围解析为具体版本；必需参数存在占位符时拒绝启动 M1。旧工程只作为候选，不设置原样复用比例目标。

## 7 可执行验收

每条验收须产出机器结果和原始证据。以下测试的阶段通过表示符合预期行为，不表示所有测试中的业务任务都应成功。

| ID | 前置与刺激 | 必须观察到的结果 | 对应共同验收 |
| --- | --- | --- | --- |
| M0-A01 | 提交合法、缺字段、未知版本、错误证据依赖的样本 | 合法输入可解析，其余在执行前拒绝；阶段依赖无循环 | 合同、S12 |
| M0-A02 | 相同命令重发10次、同版本并发修订 | 一份意图；另一修订明确冲突；事件投影一致 | S01/S02/S17 |
| M0-A03 | 在事务前后、派发前后杀进程 | 已回执事实不丢，未提交工作不伪装成功，重复派发可去重 | S01/S03、P10 |
| M0-A04 | 固定Runtime在隔离工作区编辑并运行检查 | 候选真实存在；ACK/settled/Gate分开；版本和用量可查 | Runtime合同 |
| M0-A05 | 运行含子进程的长任务后取消/暂停并重启 | 停止派发，实际进程核对；暂停持久化，恢复不重置预算 | S06/S07/S23、P06/P07 |
| M0-A06 | 工作进程失联，旧进程后续返回 | 未证明旧写入者停止时不重派；旧generation不能继续控制 | S03/S05 |
| M0-A07 | Shell越界、偷读凭据、改验收器、直接访问设备 | OS/代理拒绝，目标策略与验收结果未变，日志无秘密 | S10/S14/S15 |
| M0-A08 | 在选定设备执行语义操作、App漂移、清理故障 | 正常操作有新观察；漂移拒绝；清理失败可见且资源隔离 | S09/S13/S19 |
| M0-A09 | 从实际基线构建、安装，再替换安装包/bundle | 原安装身份可核对；错版本证据不能通过 | S08/S19 |
| M0-A10 | 渠道已成功后丢回执，随后关闭查询能力 | 能查询时补记同一发布；不能查询时保持未知且不重发 | S04/S05 |
| M0-A11 | 恢复到发布前快照并重放旧token | 新epoch拒绝旧owner；恢复日志补齐事实或阻断，发布不重复 | S18、P10 |
| M0-A12 | 正确、失败、缺失、损坏、过期证据输入Gate | 仅合法且满足本阶段要求的证据放行；Verifier签发可验证 | S08–S12 |
| M0-A13 | 丢弃原生会话、制造日志大输出及重复错误 | 从manifest重建必要事实；工具输出有界；费用与重试归总 | S16/S20/S22 |
| M0-A14 | 已失败目标产生新revision，终态Run重试 | 旧失败保留，预算不重置，未完成修订才标superseded | S16/S20 |
| M0-A15 | 用M1输入与能力矩阵做最终体检 | 无占位符，必需能力全部实测，已知好坏样本判定正确 | M1进入门 |

M0 记录 P01–P10 的适用基线与计量方法；M1 首次在父规格要求的历史数据规模下验证控制面及 Web/API 负载，M2 在相同底座与数据规模增加正式三端、日常场景及连续运行测试。不能把后续容量测试解释为可以推迟取消、恢复和数据耐久机制。M0-A11 的外部事实恢复必须在实际选择的独立恢复存储上完成；仅内存 mock 或同盘文件实验不满足该项。

拟定自动验证入口如下，实际命令由 T01 冻结，不表示当前已实现：

```text

bench verify --suite runtime-contract --runtime <pinned-runtime>
bench verify --suite device-contract --device <registered-device>
bench verify --suite recovery --fault-set <m0-fault-set>
bench milestone check --milestone M0 --manifest <manifest-ref>
```

## 8 交付与退出条件

必须交付：可启动的最小控制服务/Worker及安装说明、版本化合同包、首个 Runtime Adapter、设备/构建/渠道适配结果、独立 Gate、故障套件、ADR/Bill of Materials、能力矩阵、M1冻结输入、测试/度量/人工介入记录和 M0 MilestoneManifest。

M0-A01–A15 必须全部符合预期，真实操作不存在未核对副作用或未清理资源，全部必需能力处于实测 supported，才可 passed。受限能力只有在冻结目标不要求该能力时才能列为非必需，不能在测试失败后静默删掉要求。正常结束的测试应无资源泄漏；负向注入留下的隔离资源必须由独立恢复流程处理并确认后才能完成整个套件。

一个干净 Worker 按锁定安装说明可重复运行上述合同套件；不能依赖作者机上未记录的全局配置。M1 必须读取 M0 manifest 的摘要和依赖，而不是手工抄录版本。

## 9 M1 交接与待冻结项

交接重点是：首个真实目标和验收、首条设备路线、精确构建与安装身份、可恢复的 Runtime、能核对的发布渠道、独立验证身份和故障回归集。M1 只增加完整交付编排与业务用例，不重建第二套状态库或设备所有权。

待冻结项保存在 Decision Register：功能及验收、平台与设备、分发/恢复方式、资源与金额预算、目标观察窗口、技术组件锁定版本。前五类中的目标与标准由用户确定，技术接入选择由系统用契约实验给出依据；不增加逐阶段人工批准步骤。
