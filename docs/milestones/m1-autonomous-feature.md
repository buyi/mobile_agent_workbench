# M1 真实功能自主交付规格

版本：v0.3；日期：2026-10-08；状态：评审稿，尚未实现或实测。

上位规格：[产品与架构](../loopit-workbench-spec.md)、[执行契约](../execution-contracts.md)、[验收与评测](../acceptance-spec.md)、[参考与选型](../reference-and-selection.md)。本文细化 M1 的实现范围与放行条件，不另建状态、证据或统计协议。跨阶段交接采用[里程碑索引](README.md)定义的 MilestoneManifest。

## 1 目标与边界

M1 的交付是：在 M0 已冻结的目标、验收与执行策略下，工作台自主完成现有 Loopit 移动端一个真实小功能，从需求、设计、开发、独立验证到内部部署和运维观察；正式运行中的人工执行介入为 0。

用户已确认首验对象为“现有 Loopit 的真实小功能”。具体功能、平台、设备、渠道与预算尚未确定，本文不把诊断页样例、Android 建议或任何历史渠道视为已批准需求。它们必须在实际启动前冻结。

M1 必须证明三个事实：能交付；遇到可恢复错误会自行修复；不能完成时真实阻断。正常路径成功不能替代后两项。

**包含：** 一个经过 M0 验证的成熟 Runtime、一个控制平面、一个常驻 macOS Worker、目标指定设备、内部渠道、最小 Web 操控与事实面板。平台数量以冻结矩阵为准，每个平台分别取证。

**不包含：** 正式手机/桌面客户端、全日常场景覆盖、自动经验晋升、工作台自身升级、生产灰度及公开商店发布。这些由 M2/M3 或单独目标承担。M0–M3 使用同一开源底座，不包含第二 Runtime 建设。M1 保存后续学习需要的轨迹，但不以训练系统建设阻塞真实功能交付。

Project → Task → Run → Delivery 仍是产品模型提案。本文用这些名称指代已有合同身份；未确认的导航和界面组织不阻塞执行合同实现。

## 2 M0 输入与进入条件

| M0 交接输入 | M1 启动检查 | 不满足时 |
| --- | --- | --- |
| 冻结 GoalSpec、PolicyRef、验收条目与完整预算 | 引用均能解析，范围、终点、平台及 requiredAtStage 无占位符 | 目标保持 draft，独立只读调查可继续 |
| 版本化 schema、状态 reducer、命令与事件合同 | 兼容版本及非法转换测试通过 | 不能接受正式交付 Run |
| 锁定 BOM、选型 ADR、capability matrix | 必需能力在当前版本和目标环境已实测 supported | 替换适配器后重验，不降低验收 |
| Runtime、沙盒、停止和恢复实验 | 无交互审批依赖，子进程控制与权限边界有效 | 不得声明 autonomous |
| 构建、签名、设备和分发合同证据 | 可构建安装，能读实际包身份，发布可 inspect/reconcile | 阻塞相关交付链 |
| 受保护 Case Pack、fixture、验证器正反例 | Builder 不可修改正式标准、签发身份或故障注入器 | 不允许正式 Gate 放行 |
| 基线、观察策略、恢复策略 | 基线可复现，窗口/样本/健康阈值与补偿能力明确 | 不得用“无错误日志”代替观察 |

环境接入准备不计入正式功能运行，但单独保存耗时、人工操作和配置变更。正式计时从目标入队开始；此后设备失联、凭据失效或人工解锁都如实进入本次结果。

M0 合同通过之后，M1 仍需运行真实全链路实验；协议样例的通过记录不能充当 E01 功能交付证据。

## 3 四层增量与边界

| 层 | M1 新增职责 | 交付边界 |
| --- | --- | --- |
| 接入 | Web 目标输入、进度、验收清单、交付物、暂停/恢复/取消；最小事实面板 | 页面不拥有执行锁，不保存发布凭据；断开后 Worker 继续 |
| 编排 | 将 M0 合同组成持久六阶段交付图；预算、依赖失效、自动返工、观察定时和最终 Gate | 模型提出计划与诊断；编排只检查合法性、权限、资源、证据与状态 |
| 执行 | 一个 Runtime Adapter、独立 Verifier、构建/分发/观察执行器与恢复协调 | Runtime 管内部工具循环；默认 Builder/Verifier 串行，不自研第二套编码循环 |
| 基础 | 持久事件/产物、Operation Ledger、独立恢复日志、设备 Broker、凭据代理、沙盒及监控 | 所有设备控制经过同一 Broker；签名/发布身份和原始证据签发与 Builder 隔离 |

上下文以 ContextManifest 和产物引用交接；原生日志按需读取。工作记忆随 Run 恢复，情景记录保留失败和修复；M1 不把自动生成的复盘直接提升为可信项目规则。

## 4 功能要求

下列 MUST 为 M1 放行要求。字段及状态含义沿用[执行契约](../execution-contracts.md)。

| 编号 | 要求 | 可观察结果 |
| --- | --- | --- |
| M1-F01 | MUST 在目标入队时校验已冻结输入并完成能力体检；每次开始高风险阶段前复核必要能力 | 体检回执绑定目标、环境、策略和能力版本；不满足显示具体缺口 |
| M1-F02 | MUST 提供最小 Web 创建/查看/追加材料/修订目标/暂停/恢复/取消操作 | 持久 command 回执、版本冲突及当前连接状态可见；草稿不显示为已提交 |
| M1-F03 | MUST 以持久事件驱动六阶段与依赖图，模型输出计划经过合法性校验 | 重启后阶段、产物与预算不丢失；replay 不重跑已落账模型决策 |
| M1-F04 | MUST 用锁定 Runtime 完成需求整理、设计、编码、诊断与修复 | 原生事件和归一化事件可追溯；settled/exited 均不能直接标记业务成功 |
| M1-F05 | MUST 为每个写入 Attempt 隔离工作副本，冻结可核验 Candidate | 提交、补丁、锁文件、构建参数及允许修改范围有摘要；新写入形成新候选 |
| M1-F06 | MUST 通过统一 Broker 构建、安装、操作并观察真实 Loopit App | 设备、OS、安装包、JS bundle/OTA、fixture 与环境身份绑定证据；旧 fencing token 被拒绝 |
| M1-F07 | MUST 由独立会话/执行身份在只读候选上验证，保护标准与签发边界 | Builder 不能写正式 Case Pack、阈值、GateDecision 或证据命名空间；负样本不能放行 |
| M1-F08 | MUST 将失败证据交给模型自动诊断，在原标准下形成新候选并重验 | 每次 Attempt 保留；同一失败两次修复无新证据后必须换诊断或策略，仍受总预算限制 |
| M1-F09 | MUST 支持有依据的 reused/not_applicable；每次复用重新核对依赖与新鲜度 | StageDisposition 可下钻；未覆盖的 required 条目仍为 pending/failed/blocked |
| M1-F10 | MUST 优先验证并分发同一二进制，最终包变化时重判每条证据 | 重跑受影响验收；影响无法证明则重跑全部必需功能验收；最终安装与冒烟不可省 |
| M1-F11 | MUST 自动内部分发、核对渠道回执和安装事实，并执行冻结观察窗口 | publish、inspect、install、observe 形成可追溯链；上传完成不等于交付完成 |
| M1-F12 | MUST 在结果未知、暂停、取消、失联时停止新动作并核对旧执行 | 无双重设备控制、盲目重复发布或虚假 cancelled；无法确认的资源隔离 |
| M1-F13 | MUST 统一计量模型、Runtime 子代理、工具重试、构建、修复与等待 | 目标总预算不随新 Attempt/Run 重置；费用未知单列；耗尽后只执行预留收敛动作 |
| M1-F14 | MUST 记录每个阶段失败、目标结果、人工执行触碰及修订历史 | Web 最小面板展示分子分母、未结案状态、失败/修复次数、费用和未知项 |
| M1-F15 | MUST 在观察失败时自动执行既定停止分发或可用回滚，并核对生效 | 恢复回执绑定原部署；旧失败保留，故障候选不能因回滚成功变成成功交付 |
| M1-F16 | MUST 生成机器可读与可阅读的最终交付或失败包 | 按验收项反查 Evidence → Install/Build → Candidate；报告不依赖聊天补充解释 |

## 5 六阶段输入、输出与短路

| 阶段 | M1 固定输入 | M1 固定输出 | 本阶段推进及短路 |
| --- | --- | --- | --- |
| 需求 | 冻结 GoalSpec、项目材料、能力矩阵、PolicyRef | RequirementSpec、验收映射、约束与待解决项、计划提案 | 可复用同目标版本规格；目标或标准矛盾产生 ConstraintRequest，不能擅改 |
| UI/设计 | RequirementSpec、现有 UI/设计系统、图像或设计输入 | DesignSpec 或 NoDesignChange、关键状态/交互/视觉依据 | 无 UI 变化可不适用；复用设计必须覆盖本次受影响条目 |
| 开发 | 需求/设计产物、仓库基线、ContextManifest、计划 | 冻结 CandidateManifest、diff、变更说明、快速检查 | 已有匹配候选可复用；真实新功能不能以“无修改”短路其需求 |
| 测试/验证 | 只读候选、正式验收契约、Case Pack、fixture、目标设备 | VerificationReport、原始证据、Assessment、阶段 GateDecision | 仅完全匹配候选及依赖的有效结果可复用；失败自动返工 |
| 打包部署 | 已验证候选、BuildSpec、渠道/签名引用、恢复策略 | ReleaseManifest、最终包验证、分发/安装回执 | 同一包可复用构建；M1 交付终点要求内部部署，不能将该义务标为不适用 |
| 运维 | 已核对部署、观察策略、指标源、基线、预算余量 | ObservationReport、补偿回执、DeliveryReport 或失败包 | M1 必须完成规定窗口和最低样本；数据源不可查、样本不足不能短路 |

每阶段都提交 StageResult，合法短路也提交。阶段 Gate 只检查当前 requiredAtStage 条目；最终 delivery Gate 汇总全链路，避免上游必须先拥有下游回执才能放行的循环依赖。

运维窗口建议采用父规格的 30 分钟、30 次健康探测、10 次目标路径执行，但仅在用户目标/项目标准冻结后生效。只能报告该测试环境的结果，不能推断生产崩溃率。

若目标要求合并，合并动作纳入副作用核对；基线或合并提交变化后重验受影响条目。未要求合并时交付候选与差异，报告明确主分支状态。

## 6 自主循环与异常收敛

正常路径：目标体检 → 需求/设计 → 冻结候选 → 独立验证 → 最终包检查 → 内部部署 → 观察 → 完成资源恢复 → delivery Gate。模型修复可回到需求调查、设计或开发，但不得改变冻结目标和验收标准。

| 情况 | 必须执行的动作 | 可接受结果 |
| --- | --- | --- |
| 产品验收失败 | 固化失败证据，模型诊断，产生新候选，按依赖失效重验 | 预算内修复成功，或明确 failed；不覆盖首次失败 |
| 验证器疑似误判 | 阻断该 Gate，保留原候选；独立维护任务验证新版本 | 经正反例校准后替换并重跑；不得当前任务就地降阈值 |
| 构建或设备中断 | 查询 Supervisor/外部作业，撤销旧控制权，确认后恢复 | 延续同一 Run 事实；新 Attempt 不重复派发仍活动操作 |
| 发布成功但回执丢失 | 按 operationId/包摘要 inspect/reconcile | 找到相同发布补账；不能证明未发生则 indeterminate |
| 发布查询也失效 | 隔离该发布动作，保持未知；继续无冲突工作 | 可见 blocked/恢复中及 deadline；不重发来试探结果 |
| 取消或暂停 | 停止派发、核对进程树和外部作业，保存上下文，释放或隔离资源 | 只有停止确认后才 cancelled/paused；ACK 不等于已停止 |
| 设备离线、签名失效、磁盘满、限流 | 有界等待或策略内等价替代，耗尽则收敛 | 明确 blocked/failed/timed_out；已入队记录仍计统计 |
| 运维健康失败 | 停止分发/支持的回滚，确认实际状态，保存失败与恢复证据 | 当前失败候选不得通过；后续修复按同目标剩余预算重验 |
| 从旧备份恢复 | recovery-only、新 epoch、补齐独立恢复日志、核对渠道 | 未知副作用不重发；不能直接恢复调度运行 |

总预算必须在启动前分配正常工作、修复及收敛余量。系统对正在发生的外部动作不能保证撤销，但必须在本地阈值前停止新调用，保留最终费用差异及未核对项。

人工写代码、执行命令、重装包、解锁设备、搬运证据或改运行状态均计执行介入。初始目标/标准设定及只读查看不计；运行中改变目标产生新 revision，不能把人工救回隐藏在修订中。

## 7 实现切片与依赖

| 切片 | 输入与实现 | 独立交付/退出证据 | 依赖 |
| --- | --- | --- | --- |
| M1-I01 任务控制 | 将 M0 schema/reducer 接到持久服务；事务回执、outbox、状态和预算投影 | API 及最小 Web 可创建、控制、重连；重复命令与非法转换测试 | M0 合同与存储 ADR |
| M1-I02 执行生命周期 | 常驻 Worker、Runtime Adapter、隔离副本、ContextManifest、取消/恢复 | 一次编辑检查；停进程树；从持久事实重建；原生事件归档 | M0 Runtime/沙盒实验 |
| M1-I03 设备与构建 | Broker、安装身份、Case Pack 调用、构建/签名回执与产物提交 | 目标 App 上正负 Case；设备租约与网络/录屏恢复 | M0 设备/构建实验 |
| M1-I04 验证修复 | 六阶段依赖、独立 Gate、短路检查、证据失效、预算内诊断重试 | 已知错误被拒绝并自动修复；伪证据/篡改/越权被拒绝 | I01、I02、I03 |
| M1-I05 部署观察 | 内部分发、未知副作用核对、最终包重验、观察定时、补偿 | 可安装分发包；回执丢失不重复发布；健康失败正确阻断 | I01、I03；与 I04 共享固定证据合同 |
| M1-I06 完成交付 | 集成结果页面、最小统计、交付包与故障注入评测入口 | E01–E06、S/P 适用项、恢复演练及签名报告 | I04、I05 |

I01/I02/I03 可在 M0 合同固定后并行；I05 的渠道实现可并行于 I04，正式端到端验收必须汇合。每片先通过自身合同再接主链，不能把不可核对渠道或不可靠停止能力延后为“稳定性优化”。

首轮只启用一个写入者和一台设备的独占控制。控制面容量测试可使用模拟执行器并发；模拟结果不得替代真实功能、安装、性能回归和渠道实验。

## 8 可测验收

下表 ID 属于本文；E/S/P ID 指向[父验收规格](../acceptance-spec.md)。每项报告含输入版本、条件、预期、实际、证据与预算。notRun/环境阻塞必须单列，不能计为通过。

| 编号 | 实验与通过标准 | 父规格映射 |
| --- | --- | --- |
| M1-A01 | 给定干净真实 Loopit 基线和冻结目标，自动完成六阶段；最终安装/分发包通过全部条目与观察，人工执行介入 = 0，总预算有效 | E01 |
| M1-A02 | 自动故障注入器引入可修复错误；首次正式验证失败，系统读取证据修复新候选，在未修改标准下交付；首次失败、修复时间和费用均保留 | E02、S10、S16、S20 |
| M1-A03 | 在构建、设备验证两个注入点分别终止控制进程/Worker；重启开始核对后继续交付；无孤儿进程、双控制者和重复发布 | E03、S03、S13、P07 |
| M1-A04 | 关闭发起浏览器，任务继续；另一浏览器/API 客户端用游标重连，目标版本、事件、证据一致；正式三端切换留给 M2 重跑 | E04、S17、P05 |
| M1-A05 | 禁用必需且无等价替代的构建能力；系统预算内 blocked/failed，无伪包、伪通过、无限等待，失败分类和缺口明确 | E05、S22 |
| M1-A06 | 在内部环境注入健康故障；系统执行预定停止分发/支持的回滚并确认，当前故障候选不成功；补偿失败则保持未核对与资源隔离 | E06、S07 |
| M1-A07 | create/start/cancel 同一 commandId 各重发 10 次仅有一份逻辑意图；两客户端以相同 expectedVersion 修订，只一项成功，另一项冲突 | S01、S02 |
| M1-A08 | 外部发布成功、业务回执落账前终止 Worker；恢复按相同 operationId/包摘要核对，发布数仍为 1 | S04 |
| M1-A09 | 在 A08 基础上关闭渠道查询，系统保持 indeterminate、停止相关派发并隔离；查询恢复后正确补账，无重发 | S05 |
| M1-A10 | 取消含子进程的长命令；1 秒内停止新派发，受控本地进程通常 10 秒内停止，否则报告异常并隔离；外部不可中止作业继续核对 | S06、S07、P06 |
| M1-A11 | 暂停后重启仍暂停；恢复不重置预算，先核对旧执行、租约和证据；旧 token/延迟回执不能夺回新 generation 控制权 | S03、S23 |

| M1-A13 | 删除/损坏证据、替换摘要或尝试由受测代码签发正式回执，Gate 均不得通过；原始产物持久失败也不可仅凭摘要放行 | S09 |

## 9 交付产物与退出条件

M1 交付包必须包含：

1. 工作台可启动版本、锁定依赖、部署/恢复说明与该版本源码差异。
2. 首个功能 GoalSpec、PolicyRef、Case Pack、固定 fixture、能力矩阵与六阶段 StageResult。
3. Loopit Candidate/diff、签名包、构建/实际安装/内部渠道回执、最终包有效证据与观察报告。
4. E01–E06 及 M1-A01–A24 的全部运行结果、故障点、机器可读统计、人工介入明细和资源清理记录。
5. 从验收项到原始证据的索引；失败报告同样保留最后候选、预算、已尝试策略和未核对副作用。

M1 的 MilestoneManifest 引用已通过的 M0 manifest、当前源码/规格版本、全部测试与指标、交付产物及剩余约束；verdict 只能为 passed/failed/blocked。失败和阻塞也必须产出 manifest，必需项 notRun 不可通过。

只有全部 M1 MUST 与适用验收通过，必需能力无 notRun，E01/E02/E03 无人工执行介入，预算和恢复边界达标，才可标记 M1 完成。单例交付只证明链路存在，不作为日常覆盖率或生产可靠性的结论。

M1-A06/A09/A10/A17/A20 等负向场景可以先验证正确阻断或资源隔离；整个套件结束前还必须自动撤除注入，独立核对在途发布/旧进程，恢复设备与网络配置并生成 CleanupReceipt。真实副作用仍未知、故障残留或清理失败时，manifest 保持 blocked，不能因负向断言符合预期而直接 passed。

## 10 M2 交接

M2 接收所选唯一开源底座的版本化 API/SDK、Web 连接行为、事件和报告样本、一个实测 Runtime、设备/构建/发布扩展、错误分类及准确指标查询。三端沿用该底座，不另建任务状态或接入第二 Runtime；升级底座后重跑受影响合同。

另交付脱敏轨迹与候选经验、M1 中暴露的能力缺口、基线性能及未覆盖平台列表。M2 将其用于代表任务集、长任务/并发、正式三端 E04 和最小记忆/skill 晋升，不继承“未验证 = 支持”的假设。
